# Proposal Execution architecture seam

The orchestration layer should remain thin: proposal parsing produces normalized channel facts; task recipes produce a dependency graph; adapters are the only code that knows how a SmartHub tool is executed.

Current adapters are `brief`, `radio_scripts`, and `launch_packet`. The next implementation wave should add tool-native adapters without changing run/task state semantics.

An adapter may generate internal work automatically. Any adapter capable of publishing, scheduling, changing live media or spending money must declare an approval/handoff mode and must not report `live` or `completed` until the external action is verified.

The queue is persisted in the shared Hub database. The MVP advances from the existing scheduler leader through a bridge installed when the feature registers. That bridge is intentionally replaceable by a dedicated scheduler entry later; task storage and APIs do not depend on how the tick is delivered.

Beside the task graph the run carries a **plan** (`hub/proposal_plan.py`, stored in `plan_json`): the creative needed, the one-time launch tasks and the monthly promises, plus the questions the proposal left open. The rule-derived items always exist and read their sizes from `hub/creative_specs.py` through `hub/creative_needs.required_units()`; the model adds the proposal's specific promises and must quote the line each came from, with an unquotable one marked rather than trusted or dropped. Nothing arrives accepted — a person keeps, drops, adds and answers through `POST /api/proposal-execution/run/<id>/plan` — and only what was kept reaches a working brief or a handoff packet. The page renders a task's result as directions (summary, headed lists, a link to the tool, plumbing behind a fold), never as a JSON dump; `test_proposal_plan.py` drives that renderer in node.

A run can start from a **quote built in the Proposal Builder** as well as from an uploaded document. `hub/proposal_quote_facts.py` reads the quote's own state -- line items, dollars, start date, target areas, the creative gate's supply answers, the Reporting section's cadence -- into the same analysis shape the engine consumes, with `quote` carrying the facts the plan pre-answers from; the picker lists saved quotes first and a filed PDF resolves to the quote it was rendered from through `Quote.client_filed_as`. The plan's answers are **read by the work**: `proposal_plan.resolve()` derives due dates, suppliers and cadence onto the items at read time (served by `as_dict()`, never stored), and `answers_for()` is what `_brief_runner` and `_launch_runner` hand downstream.

Every creative item carries the **press that closes it**, decided server-side by `proposal_plan.item_actions()` from its kind and its supplier answer -- make it in the tool that makes that kind of file (`CREATIVE_TOOLS`), or the client's upload link, created only by the explicit `POST /api/proposal-execution/run/<id>/upload-link`. The plan also reaches the rest of the Hub as counts beside a link: `/api/client/execution-plan` draws the Client 360 card, and `hub/client_health.py` reads `proposal_execution.open_plan_summaries()` to raise `plan_review` and `plan_creative` issues on `/my-clients`.
