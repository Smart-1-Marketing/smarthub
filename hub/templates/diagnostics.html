Database structure

Where client data actually lives. There is no single client table — several modules build their own database engine and identify a client in their own way, so the same client can exist more than once under slightly different names. That is what makes name-matching audits report false alarms. Read from source, so it stays accurate even when a module fails to load.

Client identity

The modules key a client three different ways — Scans on a domain, Ads and Google Access on a typed business name, Image Picker on its own table. Rather than migrate four tables, the Hub derives one key on read (hub/client_key.py) and joins on that: a domain where there is one, a normalised name where there is not. This is what that join currently finds. A record with a name and no URL on file can only ever be matched to another name, so those are listed separately.

Google, ElevenLabs and Cloudinary — estimated usage

Three providers metered in something other than calls, and none of them visible here until now. ElevenLabs bills the character of script, so a 60-second read costs five times a tag. Cloudinary bills in credits, where one credit is a thousand transformations or a gigabyte stored or a gigabyte delivered — so what the Hub uploads is only part of the bill, and Cloudinary’s own meter is shown beside it as the authority. Google costs nothing; what runs out there is a daily request quota, which is why it is compared per API and per day rather than per month. A provider nothing has recorded reads not measured rather than showing a confident zero.
