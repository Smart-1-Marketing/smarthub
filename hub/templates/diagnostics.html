Environment — what actually resolved

Most settings here answer to more than one variable name, because this Hub’s environment is assembled from linked Render env groups that each named things their own way. That is why a key set as PEXELS_API works in code written against PEXELS_API_KEY — and it is also why nobody can tell which name did it. This says which one answered, and names any that were set and ignored. Values are never shown.

OAuth redirect URIs — what this Hub actually sends

Every provider matches a redirect URI as an exact string, hostname included. Three of the six below are built from whichever hostname the browser used, so a second domain answering for this service doubles what has to be registered — and the other three are built from a variable instead, so they do not follow the browser and change only when that variable is edited. Registering the first three and assuming the rest followed is how a client meets redirect_uri_mismatch on a consent screen. No client id or secret is shown.

Database structure

Where client data actually lives. There is still no single client table: modules identify a client in their own way — a typed name, a domain, a row id — and changing those columns needs a migration that create_all() does not do. What closed the gap was joining them on read in hub/client_key.py rather than copying them, so a client renamed in Knack is re-joined on the next request. A row below in gray is that arrangement working; amber and red are findings. The crosswalk lists what is joined and what has no URL on file and therefore cannot be. Read from source, so it stays accurate even when a module fails to load.

Client identity

The modules key a client three different ways — Scans on a domain, Ads and Google Access on a typed business name, Image Picker on its own table. Rather than migrate four tables, the Hub derives one key on read (hub/client_key.py) and joins on that: a domain where there is one, a normalized name where there is not. This is what that join currently finds. A record with a name and no URL on file can only ever be matched to another name, so those are listed separately.

Google, ElevenLabs and Cloudinary — estimated usage

Three providers metered in something other than calls, and none of them visible here until now. ElevenLabs bills the character of script, so a 60-second read costs five times a tag. Cloudinary bills in credits, where one credit is a thousand transformations or a gigabyte stored or a gigabyte delivered — so what the Hub uploads is only part of the bill, and Cloudinary’s own meter is shown beside it as the authority. Google costs nothing; what runs out there is a daily request quota, which is why it is compared per API and per day rather than per month. A provider nothing has recorded reads not measured rather than showing a confident zero.
